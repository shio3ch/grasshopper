## CodexでGPUカーネルを232倍高速化した記録

GPU Mode主催のQR分解カーネル最適化コンテストで、著者はCodexを活用したループ工学的アプローチにより基準実装比232倍の高速化を達成し、183名中12位を獲得した。技術的な核心はブロック化Householder法の採用で、シリアルな列処理を狭いパネル内に閉じ込め、残りの行列を3つの連続GEMM（行列積）で処理することでテンソルコアの活用を最大化している。

Codexとの協働では `/goal` コマンドでエージェント実行を自動化しつつ `/btw` で検査ポイントを設定し、1500回以上の提出を通じてパネルオーバーヘッド削減とカーネル融合を段階的に達成した。局所最適解に陥らないよう複数候補をビーム探索的に並行維持し、野心的なアイデアの試行を積極的に促す運用を行った点も興味深い。ドメイン知識を持つことで「既知の未知」がAIへの効果的なプロンプト設計に変換されるという知見は、AI支援による性能最適化全般に応用できそうだ。

詳細は [Auto-research with codex: How I achieved a 232x Faster Kernel](https://sankalp.bearblog.dev/autoresearch/) を参照。

## Claude Codeに「同じ指摘を二度させない」仕組みをhookで構築

Claude Codeを日常的に使う中で、同じ指摘を何度も繰り返されることに課題を感じた著者が、フィードバックルールをファイル化して管理するシステムを構築した。`~/.claude/feedback/` に指摘ルールを1ファイルずつ保存し、指摘された回数（count）に応じて `warn → ask → deny` と強制力を段階的に引き上げる設計になっている。

具体的には3種類のhookを使い分けており、確定ルール（count≥3）をコンテキストに毎ターン注入する「inject」、実行前に違反を検知して止める「guard」、修正されるまでセッションを終わらせない「stop-check」を組み合わせている。AIエージェントとの協働が長期化するにつれ、フィードバックの定着や運用ルールの自動化が実務上の課題になっていることを示す好例で、Claude Codeのhook機構を使った実践的なノウハウとして参考になる。

詳細は [Claude Code に「同じ指摘を二度させない」仕組みを hook で作った](https://zenn.dev/nozomi720/articles/claude_code_hooks_feedback) を参照。

## LLMのテキストウォーターマーキングの仕組み

ClaudeやGeminiなどのLLMに実装され始めた電子透かし（ウォーターマーク）技術について、その仕組みを解説する記事が注目を集めた。ウォーターマーキングは、LLMが次のトークンを選ぶ際の確率分布を秘密鍵で微かに偏らせることで埋め込まれる。具体的には「Gumbel-Maxトリック」などの手法を用い、生成される文章の品質そのものを損なわずに、統計的に検出可能な「癖」を出力に加える。

この仕組みにより、人間には知覚できない程度の変化に抑えながら、秘密鍵を持つ検出者だけがAI生成テキストを識別できるようになる。ただし言い換えや翻訳によって透かしが消えてしまう可能性があり、「AI生成の証拠」としての実用面には限界がある点も指摘されている。AI生成コンテンツの検出・帰属性が社会的な関心事になる中、仕組みそのものを技術的に理解しておく意義は大きい。

詳細は [Claude がテキストに電子透かしを入れ始めたので、LLM ウォーターマーキングの仕組みを調べた](https://zenn.dev/hellorusk/articles/3328866ca9e922) を参照。

## GitHubがワークフロー統合の新機能「agent apps」を発表

## AIが数学に強い理由は「巨大な作業記憶」にあるという分析

AIが数学的推論において人間より優れた成果を出す理由について、それは高度な推論能力そのものではなく「膨大な象徴的作業記憶」にあるとする分析記事が話題になった。人間の脳は限定的な作業記憶しか持たないため、複数の制約条件や長い計算過程を同時に保持することが難しいが、AIはコンテキストウィンドウという「巨大なノート」を使い、より多くの情報を明示的に保存・操作できる。

数学は記号によって明確に表現できる分野であるため、この作業記憶の優位性が特に顕著に現れるという主張だ。LLMの能力を「推論の質」ではなく「記憶容量とその operability（操作可能性）」の観点から捉え直す視点は、AIの得意・不得意領域を見極める上で参考になる。

詳細は [AI has access to a vastly larger working memory than the human brain](https://davidepiffer.com/p/ai-isnt-outthinking-mathematicians) を参照。

## Zshの履歴ファイルが消える謎のバグを突き止めた記録

著者が長年悩まされてきたZshの履歴ファイル消失問題を、システムコールのトレースやコアダンプ解析まで踏み込んで追跡した記録が公開された。シェル終了時に、以前実行したコマンドが履歴ファイルから消え、数千行あったはずの履歴が数行だけになる現象が繰り返し発生していたという。

根本原因は、シェル終了時にZshが履歴ファイルをコンパクト化するため完全な履歴を読み込んで書き換える処理にあった。ユーザーがCtrl+Cで中断すると `readhistfile` 関数が途中で停止して不完全な履歴を読み込んでしまい、その不完全な内容でファイルが上書きされていたのだ。`bpftrace` を用いたシステムコール追跡とコアダンプ解析により `errflag & ERRFLAG_INT` フラグの存在を特定し、割り込みによる読み込み中止が原因と判明、Zsh 5.9.2での修正につながった。地道なデバッグの好例として、低レイヤーのトラブルシューティングに関心のあるエンジニアに参考になる内容だ。

詳細は [Tracking down a Zsh history data loss bug](https://michael.stapelberg.ch/posts/2026-08-09-zsh-history-truncation-bug/) を参照。

## Unicodeに潜む「ゴースト文字」の由来

1978年、日本の経済産業省が文字コード規格JIS X 0208を策定した過程で、明確な出典を持たず意味や読み方が不明な文字がいくつか紛れ込んでしまった。これらは「幽霊文字（ゴースト文字）」と呼ばれ、長らく謎とされてきた。1997年の調査により、これらの文字は「山」と「女」を重ねた記号をコピーする際に紙の継ぎ目を誤って線と認識してしまうなど、カタログ作成過程での人的ミスによって誤って生まれたものであることが判明した。

問題は、こうした誤って生まれた文字がJIS規格を経てUnicodeにも組み込まれ、現在では世界中のコンピュータに実在しない架空の文字として潜在的に存在し続けていることだ。国際規格に一度取り込まれた誤りが半永久的に残り続けるという、文字コードの標準化プロセスが抱える構造的な脆さを示す興味深い事例といえる。

詳細は [A spectre is haunting Unicode](https://www.dampfkraft.com/ghost-characters.html) を参照。

## RISC-Vの設計思想への痛烈な批判

組み込み系エンジニアのDmitry.GR氏が、RISC-Vアーキテクチャの設計上の根本的な問題を指摘する記事を公開し議論を呼んでいる。主な批判点は、すべての機能が拡張として任意実装扱いになっており乗算・除算命令さえ必須でないためソフトウェア互換性が失われていること、割り込み処理の効率がARM Cortex-M0より劣っていること、配列アドレッシングのような基本機能が欠けていることなどだ。

さらに命令エンコーディングが散在的な設計になっている点や、圧縮命令の仕様に矛盾がある点も「設計委員会による失敗」として批判している。結論として著者は、RISC-Vは安価な組み込みマイコン市場では成功するものの、高性能計算用途には適さないだろうと予測している。オープンなISAとして注目を集めるRISC-Vだが、実装現場からはこうした設計上の課題も指摘されている。

詳細は [RISC-V: They Should Have Known Better](https://dmitry.gr/?r=06.%20Thoughts&proj=12.%20RV) を参照。

## Androidでroot不要にLinuxアプリを動かす「tawc」

TAWC（Tess's Android Wayland Compositor）は、Androidデバイス上でrootなしにLinuxのCLIおよびグラフィカルアプリケーションを実行できるツールだ。PRootの高速な代替実装である「tawcroot」、Wayland合成器、専用UIで構成されており、ハードウェアアクセラレーションを活用した描画を実現している。

インストールしたLinuxアプリはAndroidのホーム画面に追加でき、XWaylandを経由したX11アプリケーションの対応も備えている。開発にはClaudeなどのAIモデルが活用されているという点も特徴的で、モバイル環境でのLinuxデスクトップ体験を個人開発でここまで作り込めることを示す事例だ。

詳細は [Tess's Android Wayland Compositor](https://github.com/wmww/tawc) を参照。

## Java・Rust・Pythonの良いとこ取りを狙う新言語「Jaithon 3」

Jaithonは、Java・Rust・Pythonの優れた部分を組み合わせることを目指す動的実行型のプログラミング言語だ。独自のバイトコードVM上で動作し、ガベージコレクション機能を備える。「The best parts of Java merged with python」というコンセプトのもと、Javaのアーキテクチャ構造とPython・Rustの構文を融合させている。

構文面では、イミュータブルな `let` と可変の `var`、コンパイル時定数の `const`、型推論、パターンマッチング、トレイト、モダンなエラーハンドリングなどを備える。実装のほとんどがJaithon自身で書かれた自己ホスト型のプラットフォームになっており、個人開発でここまでの言語機能を実装している点は言語処理系に関心のあるエンジニアにとって一見の価値がある。

詳細は [Jaithon 3, a fast programming language with the perfect syntax](https://github.com/abhiramasonny/jaithon) を参照。
