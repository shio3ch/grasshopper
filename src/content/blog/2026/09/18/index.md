本日は、GitHubがCopilotエージェントランタイムをAIエージェント主導でRustへ全面移行した事例が大きな話題となった。セキュリティ面では、OSSセキュリティツールCrowdSecのソースコード漏洩が報告された。ハードウェア分野では富士通の次世代CPU「FUJITSU-MONAKA」やTSMCの次世代A14プロセスノードの詳細が公開され、インフラ運用ではGitLab.comのレート制限変更やUberのリトライストーム対策が注目を集めた。国内コミュニティでは、フロントエンドの新技術WebMCPやAWS Lambdaのタイムアウト検証など、実践的な技術記事が人気を集めた。

## GitHub、Copilotエージェントランタイムを丸ごとRustへ移行——コードの大半をAIエージェントが生成

GitHubは、Copilotのエージェントランタイムを80万行超のTypeScriptからRustへ全面的に書き換えたことを公式ブログで報告した。移行は128件のプルリクエストに分割され、Stephen Toub氏の監督のもとで実質1人の開発者が約4ヶ月で完了させたが、コード生成の大部分はAIエージェントが担った。ビッグバン型の書き直しではなく、段階的にインプレースで置き換える戦略を採用し、移行期間中も135回のリリースを継続してメインブランチを常時デプロイ可能な状態に保った点が特徴的だ。

技術的に興味深いのは、セッションログの分析から「エージェントはコードを変更する時間よりも証拠収集（コードベースの調査）に約10倍の時間を費やしていた」ことが判明した点である。また、プロンプトキャッシュのヒット率は96.22%に達しており、大規模かつ長時間の自律的な作業セッションにおいてコンテキスト管理がいかに効率化されているかを示している。大規模言語コードベースのAI主導リライトの実例として、今後の同種プロジェクトの参考になりそうだ。

詳細は [Migrating the GitHub Copilot runtime to Rust, using Copilot](https://github.blog/ai-and-ml/generative-ai/migrating-the-github-copilot-runtime-to-rust-using-copilot/) を参照。

## OSSセキュリティツールCrowdSecでソースコード漏洩が発生

コミュニティ主導の脅威インテリジェンス／侵入防御ツールを提供するCrowdSecが、自社のソースコードが外部に流出したことを公式ブログで公表した。セキュリティ製品を開発するベンダー自身がコード漏洩のインシデントを起こしたことで、Hacker News上でも大きな議論を呼んでいる。

セキュリティツールのソースコード漏洩は、攻撃者による検知ロジックの回避手法の発見や、脆弱性の特定につながるリスクがあるため深刻度が高い。CrowdSecはコミュニティ主導でシグネチャやルールを共有するモデルを採用しているため、透明性と信頼性の両立がプロダクトの根幹に関わる。今後の対応（鍵のローテーション、影響範囲の調査結果の開示など）が注目される。

詳細は [CrowdSec Source Code Leak](https://www.crowdsec.net/blog/crowdsec-statement-source-code-exposure) を参照。

## GitLab.com、レート制限の仕様を変更

GitLabは、GitLab.com上でのAPIおよびGit操作に対するレート制限の変更を発表した。近年のCI/CDパイプラインの高頻度化や、AIエージェントによる自動化されたAPIアクセスの増加を背景に、レート制限ポリシーの見直しが必要になったとみられる。

開発者にとっては、大規模なCI/CDパイプラインやボットによる自動化ワークフローがこの変更の影響を直接受ける可能性がある。特にセルフホストランナーを使わずGitLab.comのSaaS環境に依存しているチームは、今回の変更内容を確認し、必要に応じてリクエスト頻度の調整やキャッシュ戦略の見直しを検討すべきだろう。

詳細は [Rate limits on GitLab.com are changing](https://about.gitlab.com/blog/rate-limit-change-2026/) を参照。

## 富士通、国産次世代CPU「FUJITSU-MONAKA」を発表

富士通は、日本国内で設計・製造された次世代CPU「FUJITSU-MONAKA」の詳細を発表した。同社はスーパーコンピュータ「富岳」で採用されたArmベースCPU「A64FX」の後継として、高性能・省電力を両立する次世代プロセッサの開発を進めてきた。

MONAKAは超省電力プロセスノードを採用し、HPCやAI推論ワークロードでの活用を見据えた設計となっている。国産CPU開発は経済安全保障の観点からも重視されており、半導体サプライチェーンの多様化という文脈でも注目される発表だ。

詳細は [Fujitsu launches made-in-Japan next-generation CPU FUJITSU-MONAKA](https://global.fujitsu/en-global/pr/news/2026/09/14-02) を参照。

## TSMC、次世代A14プロセスノードの詳細を公開

TSMCは半導体関連の国際学会IEDMにおいて、次世代の「A14」プロセスノードに関する技術詳細を明らかにする予定であることが明らかになった。A14はTSMCの2nm世代よりもさらに微細化を進めたノードで、次世代のCPU・GPU・AIアクセラレータの性能・電力効率を左右する重要な技術基盤となる。

半導体の微細化はAIモデルの学習・推論コストに直結するため、A14世代の量産スケジュールや歩留まりは、NVIDIAやApple、AMDなど主要チップメーカーの製品ロードマップにも大きな影響を与える。詳細な技術情報は学会発表を待つ必要があるが、事前情報だけでも業界の関心の高さがうかがえる。

詳細は [TSMC revealing details about next gen A14 node](https://iedm26.mapyourshow.com/8_0/sessions/session-details.cfm?scheduleid=331) を参照。

## Uber、リトライストームからシステムを守る仕組みを解説

Uberのエンジニアリングブログは、大規模分散システムにおける「リトライストーム」（障害発生時にクライアントが一斉にリトライを行い、負荷が雪崩的に増大する現象）への対策を解説する記事を公開した。

リトライストームは、一部のサービスの遅延や障害が引き金となり、リトライの連鎖によってシステム全体の可用性が損なわれる典型的な分散システム障害パターンである。Uberはサーキットブレーカーや適応的なバックオフ、リトライ予算（retry budget）といった手法を組み合わせることで、局所的な障害がシステム全体に波及するのを防ぐアーキテクチャを構築しているという。大規模マイクロサービス環境を運用するチームにとって実践的な知見が多く含まれている。

詳細は [How Uber Protects Against Retry Storms](https://www.uber.com/us/en/blog/protecting-against-retry-storms/) を参照。

## 証明によりAIの誤りを防ぐ言語「Bend」が登場

CPUとGPUの両方で動作し、形式的な証明によってAIによるコード生成ミスを検出・防止することを目指す新しいプログラミング言語「Bend」が公開され、Hacker Newsで話題となった。

AIコーディングアシスタントの普及に伴い、生成されたコードの正しさをどう保証するかが重要な課題となっている。Bendは、型システムや証明機構を活用して、AIが生成したコードの意図しない挙動をコンパイル時に検出するアプローチを取っている点が特徴的で、AI時代の言語設計の一つの方向性を示す事例として注目されている。

詳細は [Bend – A language that blocks AI mistakes via proof, on CPU and GPU](https://bend-lang.com/) を参照。

## WebMCPを試したフロントエンドエンジニアの所感がZennで話題に

Zennでは、ブラウザとAIエージェントを繋ぐ新技術「WebMCP」を実際に試した所感をまとめた記事がトレンド入りした。筆者は、WebMCPがフロントエンド開発における必須技術になる可能性を指摘している。

WebMCPは、Model Context Protocol（MCP）の考え方をWebフロントエンドに応用し、AIエージェントがブラウザ上のUI操作やDOM情報を直接扱えるようにする仕組みだ。エージェント型AIアプリケーションの普及に伴い、Webアプリ側がAIエージェントとどう連携するかという設計パターンの需要が高まっており、実際に触ってみたレポートは多くのフロントエンドエンジニアの関心を集めている。

詳細は [WebMCPを試してみた感想。フロントエンドの必須技術になりそうな予感。](https://zenn.dev/chot/articles/268804cd6694ab) を参照。

## AWS Lambdaの90分タイムアウトを実際に検証した記事がZennで人気に

Zennでは、AWS Lambdaの最大実行時間（90分）の挙動を実際に検証した記事がトレンド入りした。長時間実行を要するバッチ処理やAI推論ワークロードをLambda上で構築する際の制約や挙動を、実データを交えて解説している。

サーバーレスアーキテクチャでは実行時間の上限が設計上の重要な制約となるため、実際の挙動を手を動かして検証した一次情報は実務上の価値が高い。特に長時間ジョブをStep FunctionsやECSに切り出すべきかどうかの判断材料として、多くの読者から支持を集めている。

詳細は [AWS Lambda の90分タイムアウト検証](https://zenn.dev/aws_japan/articles/lambda-90-minutes-timeout) を参照。

## OpenAI、法律分野特化のAIツール「Astra for Law」を発表

OpenAIは、法律実務に特化したAIツール「Astra for Law」を発表した。契約書レビューや判例調査など、法律専門職の業務を支援することを目的としたバーティカル特化型のAI製品とみられる。

法律分野は専門知識と正確性の要求水準が高く、AIによる業務支援の効果とリスクの両方が注目される領域だ。OpenAIが業界特化型プロダクトを相次いで展開している流れの一環であり、今後他の専門職領域（医療、会計など）への展開も予想される。
