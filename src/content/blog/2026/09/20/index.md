本日はGitHubが、Copilotエージェントランタイムを約4ヶ月でTypeScriptからRustへ全面移植した詳細な事例を公開し、大規模なAIエージェント駆動開発の実例として注目を集めた。データベース分野ではPostgres向けの高速な全文検索拡張「Tin」が発表され、セキュリティ分野ではゼロ知識証明を使って圧縮後の画像の真正性を証明する研究が話題となった。Zennでは、社内のAI活用コストを10分の1に抑えた事例や、AIネイティブなデータ分析基盤の構築記事、AI生成コードに対する「認知負債」への警鐘など、AI活用の実践知に関する記事が複数トレンド入りしている。

## GitHub、Copilotランタイムを4ヶ月でTypeScriptからRustへ全面移植

GitHubは、Copilotエージェントランタイムを約430,000行のTypeScriptから約832,000行のRustへ移植した詳細を公開した。従来はSDK利用者ごとにNode.jsプロセスを起動する必要があり、V8の起動と最低100MBのメモリ消費がオーバーヘッドとなっていた。移植は「リーフから内側へ」という方針で、TypeScript実装をRust製の薄いシムに置き換えては元のコードを削除する漸進的な手法を取り、128件のポートPRを135回のリリースに分散させることで、mainブランチを止めずに移行を完了させた。特筆すべきは、実装コードの大半をCopilotエージェント自身が生成した点で、プロンプトキャッシュのヒット率96.22%を達成しつつ、人間はアーキテクチャ設計とレビューに専念したという。Rustのコンパイラは移植中に8,678件の診断を検出し、その84%が型不一致や名前解決といった機械的なミスだった一方、所有権関連のエラーはわずか1.7%にとどまった。

詳細は [Migrating the GitHub Copilot runtime to Rust, using Copilot](https://github.blog/ai-and-ml/generative-ai/migrating-the-github-copilot-runtime-to-rust-using-copilot/) を参照。

## PlanetScale、Postgres向け全文検索拡張「Tin」を発表

PlanetScaleは、Postgres向けの高速な全文検索拡張「Tin」（Text INdex）を公開した。既存のParadeDBやpg_textsearch、Postgres標準のGINインデックスが機能不足や性能面の課題を抱えていたのに対し、Tinはブール式・フレーズ検索・あいまい検索・BM25スコアリングと同時実行更新への対応を両立させている。技術的な特徴として、文書IDを別途採番せずPostgresネイティブの`ctid`（48bitのヒープ位置識別子）をそのまま利用することでルックアップのオーバーヘッドを排除し、ページレベルのビットマップをAVX2/AVX-512レジスタに収めてPOPCNT命令によるベクトル化された集合演算を行う。ベンチマークでは既存手法に対し8〜57倍のクエリスループットを示したという。

詳細は [Tin: full-text search for Postgres](https://planetscale.com/blog/introducing-tin) を参照。

## ゼロ知識証明でJPEG圧縮後も画像の真正性を証明する「ZK-JPEG」

カメラの電子署名によるアテステーションは、非可逆圧縮やぼかし・レダクション処理を経ると署名が無効になってしまうという課題がある。これに対しeprintで公開された論文「ZK-JPEG」は、秘密の入力画像から正しくJPEG圧縮が行われたことをゼロ知識証明で示す手法を提案する。PicoZKを用いてPythonの画像編集コードをLPZK証明システム向けの回路に変換し、ぼかしやレダクションといった変換処理を圧縮処理に低コストで組み込むことで、圧縮後も画像の来歴を証明可能にした。ディープフェイク対策として画像の真正性を保ちながら実運用に耐える圧縮を両立させる試みといえる。

詳細は [ZK-JPEG: Zero-Knowledge Image Editing and Compression](https://eprint.iacr.org/2026/2039) を参照。

## 全社のAI利用をOpenCode+LiteLLM経由に統合、コストを10分の1に削減

Zennでは、ChatGPT・Claude・Cursorなど複数のAIツールが乱立し社内のプロンプト利用状況が不透明になっていた企業が、全社のAI利用をOpenCode DesktopとセルフホストのLiteLLMプロキシ（AWS ECS Fargate上）経由に統合した事例が紹介された。従業員はGoogle Workspace SSOで個別のAPIキーを発行し、LiteLLM側でLow/Mid/High/XHighの4段階のモデルティアを抽象化して提供する。例えばLowティアはOpenRouter経由のDeepSeek-V4.1-Flashにマッピングされており、企業側は利用モデルを一元管理できる。週次の予算リセットとSlack経由の追加申請フローを組み合わせた結果、高価なフロンティアモデルの濫用が抑制され、導入前と比べてコストが10分の1になったという。

詳細は [全社に OpenCode + LiteLLM を導入してコストを抑えつつ AI 活用を進めている話](https://zenn.dev/jtcc/articles/7e74fef42580a1) を参照。

## バイブコーディングでGUIが壊れる理由、5つの設計パターンで防ぐプロンプト

macOS向けAIアシスタントをAI駆動で開発してきた著者が、機能追加を重ねるうちにUIが不安定化した経験を共有した。連打で応答不能になる、キャンセル操作が意図した画面に届かない、送信処理が新規リクエストで中断されるといった問題は、AIが生成する画面同士が「勝手に」互いを直接操作し合う構造に起因すると分析する。対策として、Root配下の階層構造にコンポーネントを配置し、各コンポーネントを表示のみを担うPassive Viewとし、イベント伝播にChain of Responsibility、状態遷移の判断をステートマシンとして動くMediatorに集約する、という5つの設計パターンを組み合わせた指示をAIに与える手法を提案している。

詳細は [バイブコーディングで GUI が壊れていく理由とその対策プロンプト](https://zenn.dev/nrs/articles/9ba91aea587bf5) を参照。

## PKSHA、Claude Code主導で構築したAIネイティブなデータ分析基盤「Laplace」

PKSHA TechnologyのSREチームは、1人のエンジニアとClaude Codeによる実装で1ヶ月弱のうちにデータ分析基盤「Laplace」を構築した事例を公開した。従来はAuroraリードレプリカへの直接SQLクエリとRedashに依存しており、2.5TB規模でのクエリタイムアウトやアナリスト不足、PII保護のための過度なアクセス制限が課題だった。新基盤はBigQueryへの複数経路でのデータ集約、dbtによるraw→staging→martの変換、Lightdashによるセマンティック層、AIからの問い合わせ向けMCPサーバーという構成を取り、`dbt`のschema.ymlを唯一の意味定義source of truthとすることでBIとAIの指標定義を一致させている。PIIを含むテーブルへのクエリはMCPサーバー側でブロックする設計とし、運用2ヶ月で29名が32のダッシュボードを作成、月間運用コストは約1,150〜1,250ドルに抑えられているという。

詳細は [AI ネイティブなデータ分析基盤を作った話](https://zenn.dev/pksha/articles/5a1dc6470019d6) を参照。

## 「認知負債」への警鐘、AI生成コードの理解と責任の乖離

AIがコードを高速に生成する一方、人間の理解速度はそれに追いつかず、問題発生時の責任は組織側に残るという「認知負債」の議論がZennでトレンド入りした。OSやOSSといった外部依存とは異なり、AI生成コードは組織自身が責任を負う内製コードであるため内部理解が不可欠だが、設計・レビュー工程そのものが省略されがちな点が根本的な危険性だと指摘する。著者は、将来的に組織は自社のドメイン固有ロジック以外のコードを自ら書かなくなり、ベンダー製品や外部委託、OSSへの依存を強めていくだろうと予測している。

詳細は [認知負債の未来は？](https://zenn.dev/kabeya/articles/future-of-cognitive-debt) を参照。

## 開発フロー全体をClaude Codeの「スキル」として自動化

GitHub Issueの分析からブランチ作成、実装、検証、相互レビュー、PR提出までの一連の開発フローを、`todays-work`という名のClaude Codeスキルとして自動化した事例がZennで紹介された。スキルは複数リポジトリで使い回せるようユーザーレベル（`~/.claude/skills/`）に配置され、GitHub GraphQLによるIssue理解からCLIツール`crit`とCodexによる並行非同期レビューまで9段階の工程を経る。著者は、作業の主体が自分からAIに移り、人間はAIからの依頼への対応に回るようになったと述べており、Claude CodeとCodexを別々に操作していた従来の運用が単一のエージェント経由でのやり取りに簡素化された点を利点として挙げている。

詳細は [1日の開発の流れをスキル化してみたら、想像以上に快適だった](https://zenn.dev/tenkei/articles/9f8921926bb003) を参照。

## Skiaの描画命令をLeanで形式検証、最大18.7%高速化する最適化手法

グラフィックスライブラリSkiaは複雑で不透明な実行モデルを持ち、アプリケーション側が非効率な命令列を生成しがちだという課題に対し、Skiaの挙動を証明支援系Leanで形式仕様化した「μSkia」を用いる研究がarXivで公開された。Chrome上位100サイトの実際のプログラムから非効率なコードパターンを4種類特定し、それぞれに対する検証済みの置き換えを開発。最適化結果をμSkiaの意味論に読み戻して正しさを形式検証しながら、99件の実プログラムに対しSkiaのGPUバックエンド比で最大18.7%の高速化を、最適化自体は最大32マイクロ秒という短時間で達成したという。

詳細は [Compiler-style optimization for drawing via Skia](https://arxiv.org/abs/2603.23696) を参照。

## 小型・特化型の「System 1」モデルでコンピュータ操作を高速化する「CUA-S1」

Hacker NewsのShow HNでは、コンピュータ操作エージェント向けの小型特化モデル群「CUA-S1」が紹介された。「System 1」とは、フォームのどの項目にどの値を入れるか、ある要素を操作せず放置するかといった「速く境界の定まった判断」を指すエンジニアリング上の比喩で、大規模な汎用モデルではなくスコアリングベースの軽量モデルでこうした判断を担わせる設計思想を採る。アプリケーション側がワークフロー全体を統括し、Cua Driverが実行境界を定めて操作を担当する構成で、モデル重みはHugging Faceで、MITライセンスのソースコードは別途公開されている。コードやAPIとGUI操作を柔軟に行き来する「Computer-Use 2.0」的なエージェント設計を、コスト効率よく実現する狙いがある。

詳細は [Show HN: CUA-S1 – A System One Model for Computer Use](https://github.com/trycua/cua) を参照。
